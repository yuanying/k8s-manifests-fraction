## 増え方（§5、3 台がそろった後の 03:26:40〜03:57:04Z）

| node | 03:26Z | 03:57Z | 増え方 | 上限 1.1 GB で残る日数のめやす |
|---|---|---|---|---|
| .113 | 2.78 MB | 21.28 MB | 約 36.5 MB/時 | 約 1.3 日 |
| .112 | 1.41 MB | 6.92 MB | 約 10.9 MB/時 | 約 4.2 日 |
| .111 | 0.014 MB | 0.014 MB | ほぼ 0 | — |

- 5 分おきに測り、どの区間もほぼ一定の傾きだった。回ったファイル（`audit-*.log`）はまだ無い
- 3 台の偏りは、クライアントの長く続く接続が、どの apiserver に張られたかで決まる。最後に入れ替えた .111 には、ほとんど要求が来ていない。入れ替えや再起動のたびに偏りは変わる。3 台の合計（約 47 MB/時）が 1 台に寄ると、40 MB/時を超えることがありうる
- .113 の量の 6 割ほどは、Longhorn の manager が自分の CR（instancemanagers・nodes・engines・volumes）を `update` する出来事だった。部品の外の書き込みなので `Request`（本文つき）になっている。次に多いのは、Argo CD の application controller の Application への `patch`（.112）と、各所の `watch`・`get`（Metadata）
- 手順書の §5 のとおり、1 日目と 1 週間後にもう一度測る

## 手順書との差

- **§2.2 の etcd のバックアップを取らなかった。** 本番の render と同じ版（0.37.7）の porkadot の clone を用意したが、作業端末で gem を入れられず、porkadot を動かせなかった。本人が「バックアップは無しで進めて良い」と決めた。この変更は etcd に触らず、§6 の戻し方も restore を使わないので、戻せることは変わらない
- §2.1 の 5（`E` の行の種類）は、旧 Pod のログが回っていて起動時の行が残っていなかったため、起動時の行は比べられなかった。新しい Pod の起動時には、`audit` を含まない次の行が出た。どれも Ready になる前の起動中に出た分だけで、その後は 3 台とも出ていない
  - `options.go:205 The manifest file is empty, ignoring.`（3 台とも 1 行）
  - `handler_proxy.go:144 error resolving kube-system/metrics-server: service "metrics-server" not found` と、それに続く `Unhandled Error`（.112 と .111 で計 4〜5 行）。Service と APIService `v1beta1.metrics.k8s.io` は正常で、cache が同期する前のものとみた
- ほかは手順書どおり。porkadot のコマンドは 1 つも流していない

## 申し送り

- **.113 の増え方（約 36 MB/時）は、7 日分を残す目安を大きく超える。** 収集役（Alloy）が入るまで、.113 には 1 日強の分しか残らない。量を減らすなら policy の見直しが要る。たとえば、Longhorn のような operator が自分の CR の status を書き換える `update` を `Metadata` に下げる。policy を変えるときは、手順書 §5 のとおり、この形の PR にして §3 の形で 1 台ずつ入れる
