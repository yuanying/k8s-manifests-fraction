## 3. `install kubelet`（runbook §4.2 の 3）

### 3.1 2 回の失敗（ノードは変わっていない）

| 時刻 | 流し方 | 結果 |
|---|---|---|
| 00:52:56Z | サンドボックスの中 | rc 1。SSH の接続で `Net::SSH::HostKeyMismatch`（`fingerprint SHA256:c4tHGu…CY does not match for "192.168.1.113"`） |
| 00:58:49Z | サンドボックスの外 | rc 1。同じ |

どちらも最初のコマンド（`mkdir -p ./kube_temp`）の前の SSH の接続で止まり、ノードでは何も流れていない（Pod の控えと `/opt/bin` は前のまま）。

原因は **SSHKit 1.25.0 の known_hosts の parser**（`SSHKit::Backend::Netssh::KnownHostsKeys`。sshkit が既定で net-ssh の `known_hosts` に渡す）。

- ed25519 の行は、bundle に `ed25519` の gem が無いので parse されずに捨てられる
- hashed の行（作業端末の `~/.ssh/known_hosts` はすべて hashed）は、**最初に一致した 1 行の鍵だけ**を返す
- 作業端末の `~/.ssh/known_hosts` では、.112 と .113 は rsa の行が ecdsa の行より前にあった。sshkit は rsa の鍵だけを返し、サーバーが出す ECDSA の鍵と合わずに mismatch になった。鍵そのものは正しい（`ssh-keyscan` と一致。net-ssh 自身の `Net::SSH::KnownHosts` は rsa と ecdsa の両方を返す）
- .111 と worker 5 台は ecdsa の行が先なので当たらない。00:45Z の `etcd backup` と 00:47Z の `install kubernetes`（どちらも .111）が通ったのはこのため

ユーザーの判断で、coordinator が `~/.ssh/known_hosts` の .112 と .113 の行を ecdsa が先になるように並べ替えた（01:02Z。行の集合は同じ。控えは `~/.ssh/known_hosts.bak-k8u-stage1-20261019`）。並べ替えの後、sshkit は 8 台とも ecdsa を返すことを確かめた。

別に、**サンドボックスの中では ssh-agent のソケットが塞がれ**、net-ssh は `~/.ssh/id_ed25519` を読もうとして `ed25519` の gem が無いので認証で落ちる（並べ替えの後に読み取りで確かめた）。ユーザーの判断で、`install kubelet` はサンドボックスの外で流す（agent が使える）。
