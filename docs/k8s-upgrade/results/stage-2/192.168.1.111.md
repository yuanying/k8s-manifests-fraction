### 5.1 .111 で起きたことの見立て

- kube-apiserver の Pod は hostNetwork で、`kubernetes` Service（10.254.0.1:443）と VIP の Service `porkadot-kubernetes` の Endpoints は 3 台の `:6443`。kubelet もこの VIP に繋ぐ
- .111 の apiserver は `definition changed` の SIGTERM の 1 秒後（07:31:14Z）から 6443 で `connection refused` を返し、30 秒の猶予の後の kill（07:31:43Z）まで止まりかけのまま残った。この間 `kubernetes` の Endpoints には .111 が残っていた（Endpoints から外すのは apiserver 自身と readiness。07:33Z の時点で 3 台そろって載っている）
- そのため、10.254.0.1 と VIP への新しい接続のおよそ 3 分の 1 が .111 の閉じた 6443 に振られて `connection refused` になった。同じ時刻に .111 で起き直した controller-manager、cnidaria、speaker は、起動の最初の API の呼び出しでそれを引いて落ち、2〜3 回目で起動した。作業端末の監視の VIP の FAIL 9 回も同じ割合
- runbook §4.1 の最後の項目が「見込み」として書いていた形が、ほかのノードの controller ではなく、同じノードで起き直したコンテナに出た
- .113・.112 では、apiserver の readiness の `connection refused` は 3〜4 回で、監視の FAIL も、ほかのコンテナの 2 回目の再起動も無かった。.111 で listen をやめるのが早かった（長かった）理由は分かっていない
