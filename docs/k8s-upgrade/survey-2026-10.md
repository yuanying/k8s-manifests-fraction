# K8s を 1.29 から上げる前の現状調査（2026-10-18）

本番クラスタ `fraction` の Kubernetes を v1.29.8 から 1 マイナーずつ最新の安定版（v1.37.1）へ上げる前に、クラスタとマニフェストの状態を読み取りだけで調べた記録。
計画は同じディレクトリの `plan.md` にある。この文書は、その判断の根拠である。

- 調べた日時: 2026-10-18 02:30〜02:50 UTC ごろ
- 方法: kubectl は read-only の `fraction-auditor`（`auth can-i delete pods -A` が `no` になることを確かめた）。ノードには `ssh` で入り、読み取りのコマンドだけを使った（sudo は etcd の状態を読む `etcdctl endpoint status / health` にだけ使った）。Prometheus の値は apiserver の service proxy 経由で読んだ
- 目標の版: `https://dl.k8s.io/release/stable.txt` が **v1.37.1**（2026-10-18）
- porkadot の段ごとの変更点は、別の調査（porkadot 側の worker、タスクディレクトリの `notes/porkadot-stage-survey.md`）を取り込んだ。その結論は §6 にまとめる
- 本番には何も変更していない

## 4. 削除・非推奨の API

### 4.1 削除される API と本番の利用

1.30〜1.37 で serve されなくなる組み込みの API は、1.32 の `flowcontrol.apiserver.k8s.io/v1beta3`（FlowSchema、PriorityLevelConfiguration）だけである。

- クラスタ: FlowSchema・PriorityLevelConfiguration は apiserver が自分で作る既定のものだけ。`exempt` と `probes` の managedFields に `v1beta3` が出るが、書いたのは apiserver 自身（`api-priority-and-fairness-config-consumer-v1`）
- マニフェスト: このリポジトリ、fleet-infra、private、k8s-env のどこにも `flowcontrol` は無い
- 1.37 で `scheduling.k8s.io/v1alpha2` が削除される。alpha の API は有効にしていない（`kubectl api-versions` に無い）

CRD を含めた `alpha` / `beta` の API: `cnidaria.unstable.cloud/v1alpha1`、`gate.unstable.cloud/v1alpha1`、`longhorn.io/v1beta2`、`metallb.io/v1alpha1・v1beta1・v1beta2`、`metrics.k8s.io/v1beta1`、`monitoring.coreos.com/v1alpha1`、`nfd.k8s-sigs.io/v1alpha1`。どれも CRD か aggregated API で、K8s の版とは連動しない。Longhorn の CRD の `storedVersions` は全部 `v1beta2`。

### 4.2 `apiserver_requested_deprecated_apis`

apiserver の `/metrics` は、再起動（38 時間前）以降の分しか持たず、系列が無かった。Prometheus（保持期間 10 日）で `max_over_time(apiserver_requested_deprecated_apis[30d])` を見ると、3 台の apiserver とも次の 1 系列だけだった。

| group | version | resource | removed_release |
|---|---|---|---|
| metallb.io | v1beta1 | addresspools | （CRD なので無し） |

MetalLB は 0.14.2〜0.14.4 で AddressPool の処理と CRD を外している。本番の CRD はまだ `addresspools.metallb.io` を持っており、誰かがそれを list している。K8s の更新には関係しない。MetalLB を上げるときに CRD を片付ける。

### 4.3 in-tree のボリュームプラグイン

PV は CSI（Longhorn）25、in-tree の NFS 17、local 3。Pod のボリュームは configMap・emptyDir・hostPath・nfs・PVC・projected・secret だけ。1.30〜1.37 で削除・無効化されるもの（CephFS・RBD の in-tree、`gitRepo`、flex-volume）は使っていない。

### 4.4 kubelet・コンポーネントのフラグ

`assets/` の kubelet・apiserver・controller-manager・scheduler・kube-proxy のフラグに、1.30〜1.37 で削除されるものは無い（porkadot 側の調査で v1.37.1 の `--help` と照らした）。廃止予定は kubelet の `--container-runtime-endpoint`（削除は 1.38 に延期）。kubelet の config は `cgroupDriver: systemd`、`eventRecordQPS` は未設定（1.37 で 0 の意味が変わるが当たらない）。

### 5.2 etcd

- 3 台とも `registry.k8s.io/etcd:3.5.12-0` の static Pod（`/etc/kubernetes/manifests/etcd-server.yaml`）。DB 55 MB、3/3 healthy、リーダーは 192.168.1.112、raft index は 3 台で一致。
- 3.5 → 3.6 の前に 3.5.26 以上にする（[etcd blog: zombie members](https://etcd.io/blog/2025/zombie_members_upgrade/)）。fraction は control-plane の交換で etcd のメンバーを扱ったことがあるので、とくに当てはまる。
- 3.6 → 3.7 は 3.6.11 以上から、1 マイナーずつ（[upgrade 3.7](https://etcd.io/docs/v3.7/upgrades/upgrade_3_7/)）。3.7 では `--experimental-*` のフラグが削除され、残っていると起動しない。
- どちらも、全メンバーが新しいマイナー版になった後は、イメージを戻すだけでは戻せない（snapshot から戻すか、公式の downgrade 手順）。混在中なら前のイメージに戻せる。

### 5.3 containerd

containerd の [RELEASES.md](https://github.com/containerd/containerd/blob/main/RELEASES.md)（Kubernetes Support）:

| K8s | 推奨される containerd |
|---|---|
| 1.32 | 2.1.0+, 2.0.1+, 1.7.24+, 1.6.36+ |
| 1.33 | 2.1.0+, 2.0.4+, 1.7.24+, 1.6.36+ |
| 1.34 | 2.1.3+, 2.0.6+, 1.7.28+, 1.6.39+ |
| 1.35 | 2.2.0+, 2.1.5+, 1.7.28+ |
| 1.36 | 2.3.0+, 2.2.0+ |
| **1.37** | **2.4.0+, 2.3.0+** |

- 表は「もっともよくテストされた版」の推奨であり、外れた版が動かないという意味ではない。CRI は全段で v1。
- containerd の各系列の期限: 2.2 は Active で **EoL 2026-11-06**、2.3 は LTS で EoL 2028-04-30、2.4 は Active で EoL 2027-05-16。
- kubelet 1.38 からは CRI の `RuntimeConfig` が必須になる見込み（containerd 2.0 以上。2.2.1 は満たす）。

**アップグレードの経路**（RELEASES.md「Upgrade Path」）: 連続するマイナー版（2.0 → 2.1 など）と、連続する LTS どうし（1.7 → 2.3）だけが支えられる。**2.2 → 2.3 は直接できる。2.2 → 2.4 は飛ばしになり、支えられない**（2.3 を経る）。

**config の版**: `version/version.go` の `ConfigVersion` は 2.2 が 3、2.3・2.4 が 4。2.3 の `containerd config default` は version 4 を出し、古い版の config は起動時に移行する。**2.2 は version 4 の config を読めない**（`expected containerd config version equal to or less than 3`）。version 3 → 4 で変わるのは `[grpc]`・`[ttrpc]`・`[debug]` が server plugin に移ることで、CRI の runc の節（`plugins."io.containerd.cri.v1.runtime".containerd.runtimes.runc.options`）のパスは同じ。2.3.0 の Breaking は NRI の plugin 名の規則だけ。

**入手元**:

| 入手元 | 2.3 系 | arm64 | runc | 備考 |
|---|---|---|---|---|
| Ubuntu の archive（`containerd-app`） | 無い | — | `runc-app` 1.3.4 | noble は 2.2.1（proposed に `~24.04.4`）、25.10 は 2.2.1、26.04 は 2.2.2。Ubuntu は 26.04 でも 2.3 を出していない |
| Docker の apt リポジトリ（`containerd.io`、noble） | **2.3.3〜2.3.6**（2026-10-18 の最新は 2.3.6。upstream は 2.3.7） | ある | **同梱**（2.3.6 は runc 1.5.1） | `Provides/Conflicts/Replaces: containerd, runc`。Ubuntu の `containerd` と `runc` を置き換える。2.4.1・2.4.2 も同じリポジトリにある |
| upstream のバイナリ（`containerd-2.3.x-linux-<arch>.tar.gz`、runc は別） | 2.3.7 | ある | runc の release から別に入れる | glibc 2.35 以上の動的リンク版と静的版。apt の管理の外になり、unit も自分で置く |

- runc: Ubuntu の 1.3.4 に対し、`containerd.io` 2.3.6 は 1.5.1、2.3.7 は 1.5.2（containerd の `script/setup/runc-version`）。runc 1.3 系は 2026-10 末で upstream の保守が切れる。runc 1.4 は cgroup v1 を非推奨にし、`pids.limit` が 0 のときの扱いを変えた（明示的に 0 を設定している場合だけ影響）。
- Docker の `containerd.io` は `/etc/containerd/config.toml` を conffile として持つ（`disabled_plugins = ["cri"]` の版。前タスクの記録）。既存の config を残すには、入れるときに手元の版を選ぶ。
- **oeilvert の Docker**: Ubuntu の `docker.io` 29.1.3 が動いていて（devbox の `devbox.service` が使う）、`docker.io` は `containerd (>= 1.2.6-0ubuntu1~)` に版つきで依存する。`containerd.io` の `Provides: containerd` は版を持たないのでこれを満たさず、**`containerd.io` に置き換えると `docker.io` が外れる。** Docker の `docker-ce`（noble の最新は 29.9.1）は `containerd.io (>= 2.1.5)` に依存する。oeilvert の `third-party.sources` には Docker の jammy のリポジトリが `Enabled: no` で残っている。
- 他の 7 台は `docker.list.disabled-<日付>`（worker）か何も無し（control-plane）で、Docker のリポジトリは無効。入っているのは Ubuntu の `containerd` 2.2.1 と `runc` 1.3.4。
- unattended-upgrades は Ubuntu の origin だけを対象にしているので、Docker のリポジトリから入れたものは自動では更新されない。
- k8s-env の `raspi/` の cloud-init は Ubuntu の `containerd` を入れる（control-plane を作り直すとき 2.2 系に戻る）。
- porkadot は containerd を入れない（`setup-containerd` は config を書いて containerd を再起動するだけ）。porkadot 0.29.2 の `setup-containerd` は config version 2・3・4 と containerd 2.3 以上に対応している（`7753fd0 Support containerd config version 4`）。版の行がある既存の config は作り直さず、`SystemdCgroup` だけを直す。このリポジトリの `assets/kubelet-default/setup-containerd.sh` はそれより前の render（version 2・3 だけ）なので、使う前に 0.29.2 で render し直す。

### 5.4 cnidaria

- v0.1.1（`ghcr.io/yuanying/cnidaria-cni:v0.1.1`）。`go.mod` は `k8s.io/client-go` v0.37.0、controller-runtime v0.25.1。
- watch するのは `Pod`・`Namespace`・`Node`・`networking.k8s.io/v1` の `NetworkPolicy` と、自前の CRD `NodeNetworkPolicy`（`cnidaria.unstable.cloud/v1alpha1`）。どれも 1.37 まで残る。経路は Node の `podCIDRs`（controller-manager の `--allocate-node-cidrs`）から作る。
- client-go v0.37 で apiserver 1.29〜1.36 と話すことになるが、使うのが GA の API だけなので問題は出ないと見る。各段で dev と本番の Pod 間通信と NetworkPolicy を確かめる。
- data plane は CNI の reference plugins（porkadot の `cni_version` v1.4.1）。kubelet の版とは連動しない。

- K8s の版は各段の最新パッチ（2026-10-18 に `stable-1.3X.txt` で確認）。各段の前に確かめ直す。
- **etcd は kubeadm の既定値を追わない。** kubeadm は 1.31〜1.33 で 3.5.24、1.36 で 3.6.8 を採るが、3.6 の前の 3.5.26 以上・3.7 の前の 3.6.11 以上という etcd 自身の条件を満たさない。マイナー更新を 2 回（1.34 と 1.37）、パッチ更新を 1 回（1.30）にまとめる。
- **static Pod から API オブジェクトを参照できなくなる**（1.34 で既定で有効、1.37 で常に有効）。porkadot の bootstrap 用の kube-proxy の static Pod が `serviceAccountName` を持つ。bootstrap（新規構築・証明書切れからの復旧）でだけ使う Pod なので、稼働中の更新には効かないが、1.34 の段で直す。
- **更新の順序**: 手順書の「`install kubelet` → `install kubernetes`」は skew policy の外になる。`install kubernetes` → rollout 完了 → `install kubelet --node`（control-plane を 1 台ずつ。etcd もここで変わる）→ worker を 1 台ずつ、に直す（porkadot の 1.30 の PR で直す）。
- arm64: 全段の control-plane のイメージ、kubelet / kubectl、etcd、CoreDNS、crictl に arm64 がある。
- 本番の `porkadot.yaml` は `etcd.image_tag` を持たないので、porkadot の既定の etcd がそのまま入る。`etcd.extra_env: ETCD_UNSUPPORTED_ARCH=arm64` は警告が出るだけ（消すのは任意）。
- dev（`porkadot-dev/porkadot.yaml`）は `addons.enabled` が既定（flannel）のまま。**本番の cnidaria を dev で確かめるには、dev の `addons.enabled` を本番に合わせる必要がある。**
