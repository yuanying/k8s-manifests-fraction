# worker の OS 更新前の現状調査（2026-10-17）

本番クラスタ `fraction` の worker 5 台（braque、chirico、duchamp、oeilvert、pablo）を Ubuntu 22.04 から 24.04 へ、containerd を 1.6.8 から 2.x へ上げる前に、ノードとクラスタの状態を読み取りだけで調べた記録。
手順は同じディレクトリの `runbook.md` にある。この文書は、その判断の根拠である。

- 調べた日時: 2026-10-17 05:48 UTC ごろ（cnidaria への移行の当日の作業が終わった後）
- 方法: 作業端末から `ssh yuanying@<IP>` でノードに入り、読み取りのコマンドだけを使った（sudo は config や iSCSI セッションを読むためだけに使った）。kubectl は read-only の `fraction-auditor`（`auth can-i delete pods -A` が `no` になることを確かめた）
- 本番には何も変更していない

## 1. 結論

| 論点 | 答え |
|---|---|
| containerd の出どころ | **5 台とも Docker の apt リポジトリの `containerd.io` 1.6.8-1**（`dpkg -S /usr/bin/containerd` が `containerd.io`）。Ubuntu の `containerd` は入っていない |
| `do-release-upgrade` 後に入る containerd | 何もしなければ **`containerd.io` 1.6.8 がそのまま残る**。`do-release-upgrade` は third-party のリポジトリを無効にするので、Docker のリポジトリからは上がらず、Ubuntu の `containerd` に置き換わることもない。2.x にするには、Ubuntu の `containerd` への置き換えを明示的に行う必要がある |
| 22.04 で取れる Ubuntu の containerd | `jammy-updates` に **2.2.1-0ubuntu1~22.04.2** がある。24.04（noble-updates）と同じ 2.2.1 系を 22.04 のうちに入れられる |
| 注意: 22.04 のまま `apt full-upgrade` すると | braque・chirico・duchamp・pablo には `/etc/apt/sources.list.d/docker.list` があり、**`containerd.io` の候補が 2.4.2（Docker 版）になっている**。Docker のリポジトリを外さずに `full-upgrade` すると、意図しない Docker 版 containerd 2.4.2 が入る |
| config.toml への書き足し | **porkadot 以外の書き足しは無い**。NVIDIA Container Toolkit、独自 runtime、レジストリミラーの設定は無い。中身は containerd 1.6 の `config default`（version 2）に `SystemdCgroup = true` と `max_conf_num = 1` を足したもの。4 台は同一の内容で、oeilvert だけ古い版の既定値（`sandbox_image = "k8s.gcr.io/pause:3.2"`、`docker.io` → `registry-1.docker.io` のミラー。どちらも当時の既定値） |
| `setup-containerd` の挙動 | `version` 行のある既存の config は作り直さず、`SystemdCgroup` だけ直す。今の config は version 2 なので、**そのまま流すと version 2 の config が containerd 2.x に残る**（2.x は読み込み時に移行する）。古い既定値（`k8s.gcr.io/pause:3.6` など）も残る |
| apt の hold | **5 台とも無し** |
| kubelet の入り方 | **porkadot が置いたバイナリ**（`/opt/bin/kubelet` → `kubelet-v1.29.8`）。apt のパッケージではない。`kubelet.service` は `/etc/systemd/system/` にある。OS 更新で kubelet は変わらない |
| unattended-upgrades | 5 台とも有効（Ubuntu の origin のみ。`containerd.io` は対象外）。**oeilvert だけ自動再起動あり**（`52local-reboot.conf`、04:00） |
| `do-release-upgrade -c` | 5 台とも `New release '24.04.5 LTS' available`。`Prompt=lts` |
| cgroup | 5 台とも cgroup v2（`cgroup2fs`）。24.04 でも変わらない |

## 4. ノードに配る asset（k8s-manifests-fraction の `assets/kubelet-default/`）

`setup-containerd.sh`、`setup-node.sh`、`install*.sh` は porkadot の render が作る。`addons/`（dns、multipathd）はこのリポジトリに直接置いたもので、render では作られない。

| スクリプト | 何をするか | OS 更新で要るか |
|---|---|---|
| `setup-containerd.sh`（`porkadot setup-containerd`） | config が無ければ `containerd config default` で作る。`version` 行が無ければ退避して作り直す。あれば作り直さず `SystemdCgroup = true` だけ直す。最後に containerd を再起動 | 要る。containerd を置き換えた後に流す |
| `setup-node.sh`（`porkadot setup-node`） | `addons/` の下の install.sh を流す。addon はこのリポジトリの asset で、porkadot の render が作るものではない。dns（`porka-dummy01` と `cluster-dns.service` を書き直す）、multipathd（`/etc/multipath.conf` を書き直す） | 基本は要らない（OS 更新ではファイルが残る）。流すと addon の版で書き直される |
| `install-pkgs.sh`、`install.sh`（`porkadot install kubelet`） | apt で依存パッケージを入れる、モジュールと sysctl、証明書と `kubelet.service`、`config.yaml` を置く、**`setup-node.sh` を呼ぶ**、`kubelet.conf` を消して TLS bootstrap し直す | 基本は要らない（kubelet のバイナリと設定は変わらない）。流すと addon の版で書き直される |
| `install-deps.sh` | CNI プラグイン、kubelet、kubectl、etcdctl、crictl を取ってくる | 要らない（`/opt/bin/kubelet-v1.29.8` があれば `install kubelet` も飛ばす） |

どこまで再実行が要るかは、dev クラスタでの検証（作業単位 B）の結果で確定する。

## 5. 未確認だったことと、その後

この調査の時点で未確認だったもの。dev の検証（porkadot-dev の `docs/worker-os-upgrade/verification-results.md`、2026-10-17）と本番の確認で分かったことを添える。
